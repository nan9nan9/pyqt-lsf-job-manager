# 코드 리뷰 및 결함 수정 기록 — 2026-09-05

`AGENTS.md`의 원칙에 따라 재현 가능한 결함의 원인을 수정하고, 해당 경로의 중복 구현만 정리했다. 앞선 리뷰에서 적용한 수정도 이번 검증 범위에 포함했다.

## 프로젝트 구조와 검토 범위

운영 Python 코드 35개 파일(`lsfmgr`, `mocklsf`, `examples`, `tools`), 패키지 설정, README와 관련 테스트를 검토했다. 외부 LSF 실행과 Qt 신호 전달 사이의 수명 관리, 상태 전이, 동시 쓰기, 입력 계약을 중심으로 확인했다.

| 영역 | 책임과 검토 지점 |
| --- | --- |
| `manager.py`, `handle.py`, `jobset_core.py` | 공개 API, JobSet 핸들, 생성·편집·삭제, 신호 중계와 작업 수명 |

전체 흐름은 `Manager → Submitter/Killer/Polling → Command → LSF 또는 조회 콜백`이다. Store가 상태를 보관하고 Manager가 Qt 신호로 변경을 전달한다. 기존 모듈 경계는 유지했다.

## 리팩토링 판단

- kill 병렬성은 executor 한 곳에서 보장한다. 단일 chunk와 worker=1도 동일한 경로를 이용하며, 실제 kill 전에는 스레드를 생성하지 않는다.
- 폴링 종료는 Qt 스레드의 실제 종료 수명에 연결했다. 정지 요청 신호와 별도 완료 Event를 함께 관리할 필요가 없어졌다.
- commands 검증과 선택적 수치 검증은 기존 공통 함수를 재사용했다. API별 보정 분기는 추가하지 않았다.
- 조회 순서는 증분 데이터이므로 전역 시각 하나로 오래된 응답 전체를 버리면 다른 작업의 정상 업데이트도 잃는다. 이 때문에 원장 항목에 조회 시각 하나가 필요하며, runtime만 갱신할 때는 `dataclasses.replace`로 해당 정보를 보존한다.
- MockLSF는 상태 조건만 검사해도 서로 다른 필드의 동시 변경을 보호할 수 없었다. SQL UPDATE 범위를 실제 변경 필드로 제한했다.
- 테스트 파일의 과거 리뷰 회차별 이름 변경, 대규모 파일 분할, 추상화 추가는 결함 수정과 직접 관계가 없어 수행하지 않았다.

- 실행 환경: Python 3.12.1, PyQt5 5.15.10, Qt 5.15.2, `QT_QPA_PLATFORM=offscreen`.
- 관련 테스트: 종료·옵션·MockLSF·모니터 99개 통과. 데몬 회수 테스트는 수정 전 실패와 수정 후 통과 확인.
- 전체 테스트: **1,022개 통과, 237.04초**. 앞선 수정 상태의 976개에서 회귀 테스트 46개 증가. 대규모·동시성·재진입·종료 중 장애 테스트 포함.
- 운영 Python 코드 35개 파일의 Python 3.9 문법 파싱 통과. 이는 Python 3.9 런타임 실행 검증을 대신하지 않는다.
- `git diff --check` 통과. 패키지 메타데이터와 `lsfmgr.__version__`이 모두 0.2.0인지 확인.

```bash
QT_QPA_PLATFORM=offscreen python -m pytest -q --tb=short -o faulthandler_timeout=60
```

## 추가 검토 — kill verify의 조회 장애 판정

위 수정 상태를 다시 정독해 결함 1건을 재현·수정했다.

| 우선순위 | 재현 조건과 영향 | 수정 및 회귀 검증 |
| --- | --- | --- |
| P1 | `kill(verify=True)`에서 bkill은 수락됐는데 verify 조회(bjobs chunk 또는 콜백)가 실패하면, jobset 경로는 조회 실패 job을 '생존'으로 세어 `still_alive=N`으로 보고하고 EXIT/`killed` 마킹을 전부 건너뜀. 다음 폴링이 EXIT를 실측해도 `killed` 표식이 없어 사용자 kill과 외부 종료를 구분할 수 없고 `jobset_finished`가 통지됨. 직접 조회 경로(`_verify_direct`)는 같은 상황을 미검증(None)으로 처리해 두 경로가 불일치 | `QueryResult.query_failed`(조회 실패 job_id)를 노출하고, `_verify_in_jobset`이 조회 실패 job을 생존이 아닌 미확인으로 분류. 실측 생존자는 그대로 마킹에서 제외하고 잔존 수만 None. 전면 실패·chunk 부분 실패 두 경우 검증: `test_killer.py` |

`_kill_confirm`의 timeout 후 재조회(`_confirm_by_query`)는 이미 조회 실패를 보류로 다루고 있어 손대지 않았다. 새 관심 job의 fresh 조회(`InternalStatusSource`)는 진행 중 조회와 겹치면 콜백이 한 번 더 도는데, 진행 중 조회의 관심 스냅샷이 콜백 반환 뒤에 뜨므로 결과는 같다. 정확성 문제가 아니라 그대로 두었다.

## 검증 범위의 한계

실제 LSF 클러스터 및 MultiCluster 연결은 사용하지 않았다. 따라서 사이트별 wrapper, LSF 출력 형식, 원격 kill 왕복 시간은 운영 환경에서 추가 확인이 필요하다. PySide2·PyQt6·PySide6 런타임도 이번 실행 대상은 아니다.

사용자가 주입하는 임의 Python runner는 강제로 중단할 수 없다. runner가 자체 timeout을 지켜 반환해야 shutdown이 완료된다. 콜백 응답 병합은 로컬 조회 시작 순서를 기준으로 하며, 서버 자체가 오래된 스냅샷을 반환하는 경우까지 최신성을 보장하지는 않는다.
