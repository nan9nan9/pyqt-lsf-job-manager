# LsfJobManager 전체 설계 검토 및 리팩터링 계획

기준 커밋: `d6d0708`. 이 문서는 실행 전 계획이며, 아래 후보를 확정 결함이나
확정된 분할 설계로 간주하지 않는다. 계획 작성 단계에서는 운영 코드를 변경하지 않았다.
이후 승인에 따른 구현과 검증은 [실행 결과](full-architecture-refactor-results-2026-09-05.md)에 기록한다.

## 목표와 범위

전체 라이브러리의 책임 배치, 의존 방향, 데이터·실행 모델, API 일관성,
비동기 실행과 자원 수명을 검토하고 필요한 구조 변경을 구현한다.
최근 수정한 kill·완료 판정·추적 정리는 이 작업의 일부로 재검토한다.

범위는 `lsfmgr/` 전체 23개 Python 파일, 공개 API와 사용 예제, 설정·문서,
테스트·진단 도구다. MockLSF의 9개 Python 파일과 명령 진입점도 검증 기반으로
검토하되, 실제 LSF의 동작을 MockLSF 구현으로 정의하지 않는다.

AGENTS.md에 따라 실제 요구와 변경 이유를 먼저 확인한다. 파일 길이, 패턴 적용
여부, 테스트 통과 여부만으로 구조의 적절성을 판정하지 않는다. 전체를 검토하되,
각 수정은 확인된 책임 문제를 해결하는 데 필요한 범위로 제한한다.

## 현재 확인한 검토 출발점

- `manager.py`는 1,412줄, LsfJobManager는 65개 메서드다. 공개 API 외에 입력
  변환, 편집, 제출 준비, 신호 중계, 추적 정리, 종료 순서를 함께 다룬다.
  각각이 facade에 있어야 하는지와 `jobset_core`와의 정책 중복을 확인한다.
- `submitter.py`는 1,101줄이며 BulkSubmitter는 38개 메서드다. coordinator,
  제출 worker, 재시도 timer, context, 취소와 gate의 정산 관계를 추적한다.
- `command.py`는 826줄로 명령 실행·파싱 외에 실행 풀과 상태 조회원의 수명을
  다룬다. `internal_status.py`의 849줄에는 응답 변환, 증분 원장, 동시 조회 병합,
  timeout 인계와 failover가 있다. 기능적 필요와 책임 배치를 각각 판단한다.
- CompletionTracker는 manager 전체를 참조하며 manager의 종료 상태·서비스·
  신호를 사용한다. 분리가 결합을 줄였는지, 필요한 의존만 전달하는 것이 실제로
  더 단순한지 비교한다. callback 묶음이나 새 인터페이스 도입을 미리 결정하지 않는다.

위 수치는 읽기 범위를 정하는 정보이며, 그 자체로 리팩터링 근거는 아니다.

## 실행 순서

### 1. 전체 책임·의존·계약 지도 작성

모든 영역을 먼저 검토한다. 발견한 국소 결함을 바로 수정하느라 나머지 영역의
검토가 생략되지 않도록, 1차 전체 판단표를 완성한 뒤 구현 순서를 확정한다.

추적할 대표 흐름은 생성→제출→조회→정상 완료, 실패→재시도→포기,
선택 재제출·취소, 실행 중 편집·삭제, 콜백 조회 장애·회복, handler·후처리,
실행 중 shutdown이다. kill은 이 중 한 흐름으로 다룬다.

각 흐름에 대해 입력 검증, 대상 선택, Store 읽기·쓰기, 사용자 통지,
자원 회수의 담당자와 스레드를 표시한다. 유지하는 추가 상태에는 생성·갱신·
삭제 주체를 기록하고, 잠금 순서와 잠금 밖에서 실행해야 하는 I/O·callback을 확인한다.

산출물: 현재 의존도, API 계약표, 상태·자원 소유표, 전체 영역별 판단표.
판단은 **유지 / 단순화 / 책임 재배치 / 결함 수정**으로 구분하고 근거를 남긴다.

### 2. 목표 구조와 변경 단위 확정

확인된 문제마다 현재 책임 → 목표 책임, 제거할 중복 판단, 남겨야 하는 상태,
영향받는 호출부, 호환성·성능 영향, 검증 방법을 적는다.

기존 모듈 안의 통합·이동으로 해결하는 방식을 먼저 비교한다. 새 모듈이나
클래스는 독립된 책임을 실제로 옮겨 기존 결합과 코드를 줄이는 경우에만 선택한다.
일괄 이벤트 버스, 범용 실행 엔진, 새로운 Store backend, asyncio 전환 등을
출발점으로 삼지 않는다. 파일이나 클래스 개수 자체를 성과 지표로 쓰지 않는다.

설계 문제는 실패 테스트가 없어도 책임 중복·변경 파급·불필요한 의존을 근거로
개선할 수 있다. 결함 주장은 가능한 한 결정적 재현으로 확인한다.

산출물: 목표 의존도, 변경 전후 책임표, 순서가 정해진 구현 목록.

### 3. 책임 단위로 구현

기본 검토·구현 순서는 다음과 같다. 1차 전체 검토에서 확인된 의존성과 결함
심각도에 따라 세부 순서는 조정하되, 전체 영역의 판단을 누락하지 않는다.

1. API 입력·설정 해석과 생성·편집 책임.
2. 모델·Store 갱신 계약과 그 호출부.
3. 제출·재시도·취소의 실행 조정과 정산.
4. 외부 명령·상태 조회·캐시와 폴링 반영.
5. 완료·handler·Qt 표시·전체 종료 수명.
6. MockLSF의 독립적인 설계 개선과 문서·예제·진단 도구 반영.

각 단위는 한 가지 책임 문제를 설명하고 독립 검토·되돌리기가 가능하게 구성한다.
공개 API 변경이 필요하면 실제 호출 예의 전후 차이와 기존 사용처 영향을 먼저
제시한다. 내부 구조 변경과 무관한 호환성 변경을 섞지 않는다.

### 4. 계약·경계·성능 검증

기준 커밋의 검증 기록은 PySide6·PyQt5 각각 1,143개 통과다. 구현 단위마다
관련 테스트를 실행하고, 최종 통합에서는 두 바인딩의 전체 테스트를 실행한다.

- 정상 결과뿐 아니라 시작/완료 짝, 중복 실행·통지 방지, 부분 실패, 종료 후
  자원 해제, 삭제·재제출 전 결과의 거부를 검증한다.
- 필요한 경합은 Event·정해진 삽입 지점으로 실행 순서를 고정한다.
- Store와 모델의 계약은 Qt 없이, 공개 사용 흐름은 facade·handle과 Qt로
  검증한다. 모든 테스트를 private helper 단위로 다시 쓰지 않는다.
- 폴링 대상 수와 전체 Store 크기를 나눠 비용을 측정하고, GUI에서 실행되는
  편집·조회 비용, 조회 호출 수, worker 수, 종료 시간을 관련 변경 전후로 비교한다.
- 기존 배치 읽기·갱신과 증분 요약을 보존한다. 성능 비교는 같은 환경과 입력을
  사용하며, 측정하지 않은 경로의 성능 개선을 주장하지 않는다.
- 실제 LSF 검증과 FakeLsf·MockLSF 검증을 구분해 기록한다.

## 완료 기준

모든 검토 영역에 코드·요구사항에 근거한 판단과 검증 결과가 있어야 한다.
유지 결정도 이유를 적으며, 결함이 발견된 파일 몇 개의 수정만으로 전체 작업을
완료 처리하지 않는다. 필요한 변경 목록의 각 항목은 구현 완료 또는 근거 있는
유지 결정으로 정산한다.

최종 보고에는 변경한 책임과 제거한 중복, 유지한 구조의 이유, 공개 동작 변화,
테스트·성능 결과와 검증하지 못한 범위를 포함한다. 테스트 전체 통과를 설계의
무결성 보증으로 표현하지 않는다.
